# Архитектура CosmicFly

Документ задаёт контракты для Штурмана. Исходный код здесь не пишется.

## 1. Принципы

1. Сцена координирует, но не содержит всю логику.
2. Игровая логика по возможности не зависит от конкретной Phaser Scene.
3. Ассеты и числа приходят из `src/data` и `src/config`, не из разрозненных строковых литералов.
4. Скин отделён от правил боя.
5. Один забег — один `RunState`. После Game Over он уничтожается.
6. Звук, ввод, эффекты и столкновения живут в отдельных менеджерах и системах.
7. Каждое задание Штурмана трогает одну подсистему.

## 2. Стек

| Слой | Решение |
| --- | --- |
| Язык | TypeScript, strict |
| Сборщик | Vite |
| Движок | Phaser 3 |
| Рендер | `Phaser.AUTO`: WebGL, Canvas fallback |
| Физика первой версии | Phaser Arcade Physics |
| Звук первой версии | встроенный звук Phaser |
| Звук позже | Howler.js только если встроенного звука не хватит |
| Карты | Tiled / LDtk не подключать, пока не появится необходимость в комнатах |
| Репозиторий | Git |
| Крупные бинарные файлы | Git LFS |
| Ассеты | `public/assets/`, пути только через каталог ассетов |

## 4. Сцены

### BootScene

Ответственность:

- выбрать рендер;
- проверить базовую конфигурацию;
- сразу передать управление PreloadScene.

Не делает:

- загрузку тяжёлых ассетов;
- создание игрока;
- запуск музыки.

### PreloadScene

Ответственность:

- загрузить манифест ассетов;
- показать простой прогресс;
- не падать, если опциональный звук отсутствует;
- передать управление MenuScene.

Не делает:

- игровую логику;
- кэш забега.

### MenuScene

Ответственность:

- старт забега;
- выбор скина;
- тумблер звука и автоогня;
- показ лучшего счёта.

Не делает:

- спавн врагов.

### GameScene

Ответственность:

- создать системы и сущности текущего забега;
- каждый кадр отдавать управление системам;
- держать ссылки на группы Phaser;
- поставить бой на паузу при выборе улучшения;
- сообщить GameState о победе и поражении.

Не делает:

- расчёт урона внутри гигантского `update`;
- жёстко зашитые пути текстур;
- выбор конкретного скина по имени файла;
- прямое создание частиц в десятках мест.

### PauseScene

Ответственность:

- перекрыть ввод боя;
- продолжить, выйти в меню.

Может быть наложена поверх GameScene. В этапе 1 допустима пауза внутри GameScene, если отдельная сцена ещё не создана. Отдельная PauseScene предпочтительна с этапа 2.

### GameOverScene

Ответственность:

- показать счёт, причину завершения, лучший результат;
- дать «Ещё раз» и «Меню»;
- не оставлять живой RunState.

## 5. Сущности

### Player

Хранит:

- Phaser-спрайт или контейнер;
- ссылку на `ShipRuntime`;
- текущий скин;
- флаги неуязвимости и смерти.

Делает:

- читает желаемый вектор движения от InputManager;
- применяет ускорение и ограничение скорости;
- поворачивает визуал к прицелу;
- принимает урон только через публичный метод.

Не делает:

- спавн врагов;
- выбор улучшений;
- расчёт волн.

### Enemy

Хранит:

- идентификатор типа из данных;
- здоровье;
- правило поведения;
- награду за уничтожение.

Делает:

- следует своему поведению;
- стреляет только если поведение это разрешает;
- умирает через общий канал, чтобы сработали эффекты и награды.

Не делает:

- знание о конкретных модулях игрока.

### Projectile

Хранит:

- владельца: игрок или враг;
- урон;
- срок жизни;
- флаги: рикошет, взрыв, цепь;
- идентификатор эффекта попадания.

Делает:

- летит по правилу оружия;
- при столкновении сообщает CollisionSystem;
- возвращается в пул.

Не делает:

- поиск всех врагов каждый кадр, если это не его тип.

### WeaponSystem

Ответственность:

- читать `WeaponDef` и статы корабля;
- соблюдать интервал выстрела;
- создавать снаряды через фабрику, а не `new` в сцене;
- запускать вспышку выстрела через EffectsManager.

Не хранит баланс в константах класса, если он уже есть в данных.

### CollisionSystem

Ответственность:

- столкновения игрока с врагами;
- столкновения снарядов;
- столкновения с метеоритами;
- подбор искр;
- иммунитет после удара;
- порядок слоёв: щит, затем корпус.

Не рисует эффекты сам, а просит EffectsManager.

### SpawnSystem

Ответственность:

- читать `waves.ts`;
- не спавнить в безопасной зоне игрока;
- держать лимит живых врагов;
- запускать босса один раз по правилу волны.

Не меняет статы игрока.

### IntroSequence

Ответственность:

- владеть спрайтом станции, отдельным визуалом взлетающего корабля и подсказкой;
- проигрывать фазы Hold → Launch → Depart → AwaitInput;
- вычислять позы как чистую функцию накопленного времени без твинов и таймеров;
- перекрывать корабль станцией через depth-слои и альфа-канал спрайта станции.

Не делает: не читает ввод, не касается `Player`, физики, спавнов, дистанции и HUD.

### UpgradeSystem

Ответственность:

- по повышению уровня собрать 3 предложения;
- применить выбранный `UpgradeDef` к `ShipRuntime`;
- попросить StatComputer пересчитать статы;
- сообщить SynergySystem о возможной активации.

Не открывает UI сам. UI слушает событие «нужен выбор».

### AudioManager

Ответственность:

- один музыкальный канал;
- отдельные каналы эффектов;
- громкость и mute;
- не запускать два трека музыки сразу;
- переживать отсутствие файла.

Запускает музыку только после пользовательского жеста.

### EffectsManager

Ответственность:

- вспышки выстрела;
- взрывы;
- попадания;
- след двигателя;
- экранный shake.

Все эффекты вызываются по идентификатору из `effects.ts`.

### SkinManager

Ответственность:

- применить `SkinDef` к контейнеру игрока;
- сменить текстуру, масштаб, след, вспышку носа;
- не менять боевые статы.

### GameState

Ответственность:

- хранить глобальные настройки;
- хранить лучший счёт;
- создавать и уничтожать `RunState`;
- давать сценам единую точку чтения.

Не является синглтоном Phaser. Передаётся явно.

`RunState` внутри GameState:

- счёт;
- уровень;
- опыт;
- номер волны;
- статус: playing, upgrade, paused, victory, defeat;
- ссылка на `ShipRuntime`;
- список активных синергий.

### CheckpointManager

В первой версии не активен. Контракт резервируется:

- не сохраняет забег на диск;
- может позже фиксировать безопасные точки между боссами;
- не подменяет RunState скрытым автосейвом без явного задания.

## 6. Потоки данных

Старт забега:

```text
MenuScene → GameState.startRun() → GameScene.create()
  → SkinManager.apply()
  → SpawnSystem.start()
  → AudioManager.playMusic()
```

Старт нового полёта (`startKm === 0`):

```text
MenuScene → GameScene.create()
  → player.setDormant(true)
  → starfieldSystem.setScrollEnabled(false)
  → IntroSequence.start()
  → (Hold / Launch / Depart / AwaitInput)
  → movement key → IntroSequence.stop() → finishIntro()
  → player.setDormant(false)
  → starfieldSystem.setScrollEnabled(true)
  → SpawnSystem.start() / MeteorSystem.start()
```

Старт с чекпоинта (`startKm > 0`) пропускает катсцену и сразу вызывает `SpawnSystem.start()` / `MeteorSystem.start()`.

Кадр боя:

```text
GameScene.update
  → InputManager
  → Player movement
  → WeaponSystem
  → Enemy behaviors
  → CollisionSystem
  → SpawnSystem
  → EffectsManager
  → HudView
```

Повышение уровня:

```text
Pickup → RunState.addXP
  → UpgradeSystem.requestChoices
  → RunState.status = upgrade
  → UpgradeSelectView
  → UpgradeSystem.apply
  → SynergySystem.evaluate
  → RunState.status = playing
```

Смерть:

```text
Player.hull = 0
  → EffectsManager.death
  → AudioManager.stopMusic
  → GameState.endRun(defeat)
  → GameOverScene
```

## 7. Конфигурация вместо жёсткой логики

Запрещено размазывать по коду:

- пути файлов;
- урон;
- здоровье врагов;
- ключи скинов;
- идентификаторы эффектов.

Разрешено:

- `assetKeys.ts` как единственный словарь ключей Phaser;
- `data/*.ts` как таблицы контента;
- позже JSON, если таблиц станет много, но на старте достаточно TS-модулей с константными объектами.

## 8. Ограничения первой реализации

Пока проект пустой, Штурман не реализует всю архитектуру сразу.

Первое задание создаёт только каркас:

- Vite + TypeScript + Phaser 3;
- сцены-заглушки;
- GameState без боя;
- каталоги `src/` и `public/assets/`;
- запуск через dev-server.

Сущности боя, оружие, враги и улучшения приходят отдельными заданиями.
